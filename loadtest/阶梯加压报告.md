# IT 运维工单 Agent —— 阶梯加压与容量拐点报告

> 测试时间：2026-10-20 21:42–21:47
> 被测服务：`http://127.0.0.1:8010`（独立库 `loadtest/loadtest.db`，`LLM_MODE=mock`，零外呼）
> 压测工具：JMeter 5.6.3（本机 CLI，`-n` 模式）
> 施压机与被测机同机：16 逻辑核 / 15.2 GB，因此高并发档的绝对吞吐含 JMeter 自身 CPU 争用

---

## 一、为什么拆成两条曲线

只读接口命中 30s TTL 缓存，只测读接口会得到"很好看但没意义"的数字；而写路径每提交一张工单就要跑一整套 Agent（多次库写）。上一轮混合压测（10 读 + 10 异步写 + 2 同步写 = 22 并发）已经暴露读接口 P95 被拖到 1.26–1.85s，因此本次拆成两组独立阶梯：

| 扫描 | 固定项 | 变量 | 目的 |
|---|---|---|---|
| A 只读阶梯 | 写线程组全部关闭（`wthreads=0`、`sthreads=0`） | 读并发 1/5/10/20/40/80 | 找读路径自身的容量上限 |
| B 写压阶梯 | 读并发固定 2（每轮 240 个读样本作背景探针） | 异步写并发 1/2/5/10/20 | 找写路径拐点，并量化它对读的影响 |

统一参数：`ramp=0`（瞬时同时起并发，模拟"x 人同时提交"）、读 `loops=50`（A）/ `loops=20`（B）、写 `wloops=20`。

| 80 | 24,000 | 37.8 | 635.1 | 124.9 | 119 | **172** | 246 | 743 | 0.00 |

**判定**：并发 10 → 20 时吞吐不升反降（×0.79）、P95 涨到 ×2.68，满足拐点规则（吞吐增幅 <10% 且 P95 涨幅 >50%）。

- **只读容量拐点 ≈ 10 并发**，稳定吞吐约 **570 req/s**。
- 40/80 并发档吞吐在 480–635 之间震荡（同机施压 + GIL + 单进程 uvicorn），本质是"再加人也不涨"。
- 值得肯定的是：即使 80 并发，只读 P95 也只有 **172 ms**，仍在 300 ms SLA 内，且 **0 错误**。这说明缓存 + 轻量列查询的优化是有效的。

**判定**：写路径的拐点在 **1 → 2 并发之间**，即"只允许 1 条 Agent 流水线并发写库"。

- 提交 P95 从 50 ms（1 路）跳到 642 ms（2 路），之后每加一档近似线性恶化；
- 读 P50 全程稳定在 5–6 ms（缓存命中），但**读 P95 从 170 ms 涨到 3.5 s**，尾部延迟放大 20 倍 —— 典型"多数请求很快、少数请求被写锁卡住"；
- 20 路写时提交自身出现 **0.5% 错误、最大 8.96 s**。

## 四、根因（有日志证据）

后台 Agent 处理失败 7 次，日志原文：

```
2026-10-20 21:47:32 | ERROR | itops.api | 后台 Agent 处理失败：21286
sqlite3.OperationalError: database is locked
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) database is locked
```

`logs/app.log` 中 `database is locked` 共 16 处（含异常链），与 `/api/metrics` 里 `tasks.failed` 9 → 16 完全对应。

链条：

1. 一次工单处理要多次写库（建单、状态流转、Agent 轨迹、处理日志），SQLite 同时只允许一个写者；
2. 写事务持有连接直到提交，`busy_timeout=5000` 让抢锁的请求**一直等**而不是快速失败；
3. 等锁的连接把连接池（`pool_size=10 / max_overflow=20`）占满；
4. 写路径的缓存 `invalidate()` 又让读请求回源查库 —— 回源读同样排队；
5. 结果：读 P50 不变（命中缓存）、读 P95 崩塌；写并发超过 1 后提交延迟线性上涨，超过 5s 等待上限即报 `database is locked`。

WAL 模式只解决了"读不被写阻塞"的一部分场景，**写与写之间仍然串行**，这是 SQLite 的架构边界，不是参数没调好。

## 五、结论

| 维度 | 结论 |
|---|---|
| 只读容量 | 拐点 ≈ **10 并发**，饱和吞吐 **≈570 req/s**；80 并发下 P95 **172 ms ≤ 300 ms**，全部成功 |
| 写入容量 | 拐点 ≈ **1 路并发 Agent**；2 路起提交 P95 破 600 ms，20 路时 P95 4.8 s、错误率 0.5% |
| 混合场景 | 22 并发（10 读 + 10 异步写 + 2 同步写）下读 P95 1.26–1.85 s，远超 300 ms |
| 瓶颈定位 | **SQLite 单写者锁 + 写事务占满连接池**，而非 FastAPI 或读接口实现 |
| 简历口径 | "只读 P95 全部 ≤300 ms" 仅在**无并发 Agent 写入**时成立；混合写入场景需如实写为 P95 1.3–1.8 s，并说明瓶颈与生产方案 |

**生产改进优先级**：① 换 PostgreSQL（行级锁，写不再全局串行）；② 写路径改任务队列（如 Redis + 单消费者批量提交），把并发的随机写合成顺序批量写；③ 检索/读接口保持缓存，进一步降低回源概率；④ 缩短 `busy_timeout`，让过载快速失败而不是排队雪崩。

## 六、复现命令

```powershell
# 只读阶梯（A）
foreach ($t in 1,5,10,20,40,80) {
  & "D:\rj\JMeter\apache-jmeter-5.6.3\bin\jmeter.bat" -n -t loadtest/itops_load.jmx `
    -l "loadtest/results-t$t.jtl" -j "loadtest/jmeter-t$t.log" `
    "-Jthreads=$t" "-Jloops=50" "-Jwthreads=0" "-Jsthreads=0" "-Jramp=0"
}

# 写压阶梯（B）
foreach ($w in 1,2,5,10,20) {
  & "D:\rj\JMeter\apache-jmeter-5.6.3\bin\jmeter.bat" -n -t loadtest/itops_load.jmx `
    -l "loadtest/write-t$w.jtl" -j "loadtest/jmeter-w$w.log" `
    "-Jthreads=2" "-Jloops=20" "-Jwthreads=$w" "-Jwloops=20" "-Jsthreads=0" "-Jramp=0"
}

# 出表
py loadtest/analyze_jtl.py loadtest/results-t1.jtl loadtest/results-t5.jtl loadtest/results-t10.jtl `
  loadtest/results-t20.jtl loadtest/results-t40.jtl loadtest/results-t80.jtl
py loadtest/analyze_jtl.py --detail loadtest/write-t1.jtl loadtest/write-t2.jtl `
  loadtest/write-t5.jtl loadtest/write-t10.jtl loadtest/write-t20.jtl
```

> 注意：`-J` 参数在 PowerShell 里必须加引号，否则 `-Jthreads=20` 可能被拆成 `-Jthreads=20` 之外的碎片导致参数失效。
> B 组每轮跑完需等 `/api/metrics` 的 `tasks.running` 归零再进下一档，否则上一档的 Agent 积压会污染下一档数据。

## 七、口径与局限

- 读样本每档 A 组 300–24,000 个，分位数可信；B 组每轮仅 240 个读样本，P95 实为第 12 差的样本，趋势可信、绝对值有抖动。
- B 组提交为异步 202 接口，返回时间反映"建单落库 + 抢写锁"，**不含**后台 Agent 完整耗时；Agent 单次完整耗时需看 `POST /api/tickets`（同步）或任务状态。
- 施压机与被测机同机，80 并发档 JMeter 自身占用可观 CPU，绝对吞吐偏保守。
- 全部数据落在一次性库 `loadtest/loadtest.db`，`data/itops.db`、`data/benchmark.db` 未被写入（已验证修改时间与哈希未变）。
